# 兼容性审查

在合并或发布遗留数据输出相关变更前，使用本技能做兼容性审查。

## 输入

- 代码差异或设计方案。
- 消费者契约表。
- 基准输出。
- 新需求和功能开关。
- 可用的测试结果。

## 审查重点

优先检查具体破坏风险：

- 文件名、目录、覆盖/追加行为和产出时机变化。
- 字段新增、删除、重命名、重排、分隔符变化或编码变化。
- 日期格式、时区、排序、数值精度、舍入规则和空值表示变化。
- 缺失日期、重复行和必需字段为空时的行为变化。
- 退出码、日志量、stderr 输出或半成品文件行为变化。
- 影响部署、调度或可复现性的新依赖。

## 输出格式

先按严重程度输出问题项：

- 严重程度。
- 受影响文件或契约。
- 风险。
- 来自代码差异、设计或测试的证据。
- 必要修复或缓解措施。

随后补充：

- 开放问题。
- 发布前必须补充的测试。
- 剩余风险。

## 作为子代理任务时

本节点适合强委派给子代理，因为兼容性审查需要独立视角，能降低主代理在自己设计或实现后自证正确的风险。

子代理可以：

- 阅读设计、代码差异、消费者契约和测试结果。
- 输出兼容性风险问题项。
- 建议阻断发布的问题和必须补齐的测试。

子代理禁止：

- 直接修改代码或测试。
- 批准破坏性变更。
- 将缺失证据的兼容性判断标为通过。

必须交回：

- 按严重程度排序的问题项。
- 每个问题项对应的契约或未知消费者风险。
- 必须修复项、可接受剩余风险和开放问题。
- 发布前验证清单。

## 验收标准

- 审查问题项必须能追溯到已知消费者契约或已记录未知项。
- 没有基准文件差异对比或明确审批时，不接受兼容性关键变更。
- 即使是增量新输出，也要检查运行风险。
