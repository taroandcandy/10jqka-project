# 功能扩展设计

当遗留数据脚本需要从单一旧能力扩展到新业务能力时，使用本技能。本节点专门对应工作流中的“扩展”阶段，避免把扩展需求隐含在重构或测试节点里。

## 输入

- 入口地图。
- 下游消费者契约表。
- 旧行为基线和基准输出。
- 新需求清单。
- 脏数据处理规则。
- 旧输出兼容约束。

## 执行步骤

1. 区分旧路径和新路径：旧单股票输出默认保持不变，新能力通过新增参数、新输出或功能开关进入。
2. 设计多股票批处理：按股票代码分组，单股票内按交易日期排序后计算指标。
3. 设计行业级输出：先计算单股票指标，再按行业聚合，避免把不同行业或不同股票的数据直接混算。
4. 设计停牌缺失数据处理：明确缺失交易日是否补齐、是否前向填充、是否进入诊断输出。
5. 设计重复行和空字段处理：明确错误、隔离、跳过、保留最后一行等策略，并保证结果确定。
6. 设计输出兼容：旧输出的文件名、字段顺序、日期格式、数值精度、排序、编码和空值表示保持稳定。
7. 设计新增输出：行业聚合、批处理结果、诊断信息优先写到新增路径，避免污染旧下游。

## 输出格式

输出一份扩展设计表，包含：

- 新能力名称。
- 输入变化。
- 处理规则。
- 输出变化。
- 是否影响旧输出。
- 兼容保护措施。
- 验收标准。
- 需要确认的问题。

同时输出：

- 旧行为保持项。
- 新行为新增项。
- 风险和缓解措施。
- 与后续重构切片的衔接建议。

## 作为 subagent 任务时

本节点适合受控委派给 subagent。subagent 可以草拟扩展方案，但最终业务规则和旧输出兼容边界必须由主代理确认。

subagent 可以：

- 草拟多股票、行业输出和停牌处理设计。
- 标记每项扩展是否影响旧输出。
- 提出新增输出路径和诊断输出建议。

subagent 禁止：

- 独自决定破坏旧输出。
- 独自批准缺失交易日填充策略。
- 把重构方案等同于功能扩展方案。

必须交回：

- 扩展设计表。
- 旧行为保持项和新行为新增项。
- 需要主代理或用户确认的业务规则。
- 兼容风险和测试建议。

## 验收标准

- 多股票批处理、行业输出、停牌缺失数据处理均有明确设计。
- 旧输出兼容策略清晰，不依赖口头承诺。
- 每个新行为都有验证方式。
- 设计结果能进入 `refactor-slicer` 拆分为小步实现。
