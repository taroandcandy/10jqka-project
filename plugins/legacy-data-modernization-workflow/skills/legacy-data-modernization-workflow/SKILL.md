# 遗留数据脚本现代化工作流

当用户需要一套完整、可控的遗留数据处理脚本改造流程时使用本技能。典型场景是：文档不足、测试不完整、旧输出已经被下游报表或批处理任务依赖。

## 核心模型

把工作流视为对多个单点技能的编排，而不是一个巨大的提示词。每个节点都必须产出可审阅的具体工件，供下一个节点消费。

默认节点顺序：

1. 使用 `repo-entrypoint-mapper` 梳理入口。
2. 使用 `consumer-contract-mapper` 梳理输出消费者。
3. 使用 `legacy-behavior-characterizer` 刻画旧行为。
4. 使用 `dirty-data-case-designer` 设计脏数据样例。
5. 使用 `refactor-slicer` 拆分功能扩展和重构计划。
6. 使用 `compatibility-reviewer` 审查兼容性风险。
7. 使用 `gray-release-planner` 规划灰度发布和回滚。

## 工作流门禁

在以下门禁满足前，不建议进入实际实现：

- 已识别入口、运行参数、调度任务和配置文件，或明确标记为未知。
- 已识别输出消费者和输出契约，或明确标记为未知。
- 已捕获旧输出样例作为基准文件，或记录无法运行旧路径的原因。
- 已定义缺失交易日、重复行、空字段和行业聚合的新行为。
- 已记录文件名、字段、排序、日期格式、数值精度、编码和退出行为等兼容约束。
- 已定义回滚条件和恢复旧路径的方法。

## 期望编排输出

输出一份简洁的计划或说明文档，包含：

- 工作流阶段。
- 该阶段所需输入。
- 使用的技能节点。
- 产出的工件。
- 验证方法。
- 风险和停止条件。
- 该工件如何进入下一阶段。

如果进入代码实现，每个实现步骤都要足够小，可以独立审查和回滚。

## 约束

- 先保护旧行为，再扩展新能力。
- 优先使用功能开关、兼容适配层和新旧并行输出，避免一次性大重写。
- AI 输出必须可审计：提示词、假设、生成工件和人工验证方式都要记录。
- 如果 AI 建议大范围重写，除非用户在理解兼容风险后明确接受，否则应收敛为小步迁移方案。
